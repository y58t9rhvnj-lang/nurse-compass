# 01 Compass Version1 Specification（Version1 学習フロー仕様）

Version 1.0
Last Update: 2026-07-12
Status: Specification（機能設計の基準）

> 本書は Version1 が「学生に何を体験させ、何をさせないか」を定義する。
> 上位思想は `docs/00_Compass_Charter.md`、情報の扱いは
> `docs/02_Information_Card_Model.md` を参照すること。

---

## 1. Version1 の学習ゴール

Version1 の最終的な学習ゴールは、次の一点である。

```
患者に起こっている看護問題が、
なぜ生じているのかを、学生自身の言葉で説明できる。
```

Version1 は、この「説明できる状態」に学生を到達させるための
思考プロセスを一続きの体験として提供する。

---

## 2. 学習フロー全体像

Version1 は、次の流れを一本の学習導線として構成する。

```
患者との対話
   ↓
電子カルテ
   ↓
情報収集ノート（情報整理ノート）
   ↓
様式2
   ↓
様式3
   ↓
病態関連図を参照
   ↓
患者関連図を作成
   ↓
患者に起こっている看護問題が、なぜ生じているのかを説明する
```

各段階は分断された作業ではなく、
「情報カード」を共通の通貨として受け渡していく一連の思考である
（`docs/02_Information_Card_Model.md` 参照）。

各段階を通じて、学生は必要に応じて **患者との対話** や **電子カルテ** に
何度でも戻れる。フローは一方通行ではなく、往復を前提とする。

---

## 3. 各段階の教育的役割

### 3.1 患者との対話

- 学生が最初に向き合うのは患者であり、カルテではない。
- 対話を通じて、患者を一人の人として観察し、違和感・疑問を持つ。
- ここで得た気づきが、以降のすべての情報収集の起点になる。
- Coach は答えを与えず、問いによって観察と思考を支える。
- （Sprint10.7 実装：患者との自由対話、主ルート＋話題の段階的開示、
  発言に紐づく関連情報カードの提示。）

### 3.2 電子カルテ

- 患者との対話で生まれた疑問を「確認し、深める」ために開く。
- カルテは答えの一覧ではなく、仮説を検証する参照先である。
- 学生は必要な情報を自分で探し、必要なものだけを情報カードとして拾う。
- タブ構成：診療録・患者情報・生活歴・エピソード・看護記録・OT・PSW・
  フローシート・検査・処方（`lib/chartTabs.ts`）。

### 3.3 情報収集ノート（情報整理ノート）

- 患者・カルテ・観察から集めた情報カードを、学生の判断で集約する場。
- 情報を「並べ、見比べ、意味を考える」ための作業台。
- ここで学生は「データ」を「情報」へ整理し、そこから「手がかり」を見いだす
  （`docs/03_Information_Organization_Workspace.md` §3「データ → 情報 → 手がかり」モデル）。
- Compass は整理と表示を助けるが、情報の解釈は行わない。
- （Sprint10.7 実装の起点：気づきメモ `lib/notes.ts`。情報カードモデルへの
  拡張は Version1 で段階的に行う。）

### 3.4 様式2

**役割：患者の全体像を初期的につかむ。**

- 患者の**これまでの経過・背景**を整理する。
- **初期的な全体像**を得る。
- 起こりうる**看護問題の方向性**を考える。
- ただし、**この段階で完成したアセスメントを書かせない。**
  様式2はあくまで「方向づけ」であり、結論の場ではない。

### 3.5 様式3

**役割：様式2で見えた方向性に沿って、深めるための情報を集め直す。**

- 様式2で特定した方向性に基づき、
  **より深いアセスメントに必要な情報を収集・整理する。**
- 学生は不足情報を補うために、**患者やカルテへ戻ってよい**（往復前提）。
- 学校の様式構造に従う：

  ```
  情報（S・O）
  解釈・分析
  診断の手がかり
  ```

- S（主観的情報）・O（客観的情報）は、出所を保持した情報カードから構成する。
- 「診断の手がかり」は、`docs/03` の「手がかり（Cue）」に対応しうる。
  ただし「データ・情報・手がかり」と様式の各列を機械的に一致させず、
  学校での実際の使われ方を検証しながら調整する。

### 3.6 病態関連図を参照

- **一般的な病態関連図は、教育者／開発者があらかじめ用意し、自動表示する。**
- これは「一般知識」としての提示であり、
  この段階では患者個別の解釈を含まない。
- 学生は一般病態図を参照しながら、
  「この患者ではどうか」を次段階で自分で考える。

### 3.7 患者関連図を作成

**役割：一般病態と個別患者を、学生自身の手で接続する。**

- 学生は病態関連図の上に、**患者個別の付箋（sticky note）を追加できる。**
- 付箋は次のいずれかで入力する：
  - 直接入力する
  - 情報整理ノート（情報カード）から選択する
- 学生が付箋を**配置し、矢印でつなぐ。**
- システムは**線を引く操作を補助してよいが、関係性を自動で決定してはならない。**
  「何と何がつながるか」を決めるのは学生である。
- 目標は、**「なぜその患者に看護問題が起きているのか」を、
  関連図として学生自身が表現すること。**

### 3.8 説明する（学習ゴール）

- 完成した患者関連図をもとに、
  患者に起こっている看護問題が**なぜ生じているのか**を説明する。
- ここで初めて、Version1 の学習ゴールが達成される。

## 4. Version1 が「やらないこと」（明確な非対象）

Version1 は、学生の思考を代行する次の自動化を **実装しない**。
これらは Charter の原則「学生の思考時間を奪わない」に直接反する。

- **アセスメントの自動生成・自動記述**（様式2・様式3の本文を書かない）
- **看護問題の自動選定**（問題を選んで提示しない）
- **優先順位の自動設定**（問題の順位づけをしない）
- **関連図の自動完成**（付箋の自動配置・関係性の自動決定をしない）
- **看護計画の自動生成**

Compass は情報を「整理・表示」することはあっても、
学生の代わりに「解釈・判断・結論」を行わない。

---

## 5. 設計上の含意

- すべての段階で、情報は**情報カード**として出所を保持したまま受け渡される
  （`docs/02_Information_Card_Model.md`）。
- 同じカードが情報整理ノート・様式2・様式3・関連図で参照されても、
  **独立した別コピーを増やさない。**
- 各段階の UI は「次に何を考えるか」を支援する。
  情報量を増やすことは目的ではない（`docs/05_Thinking_Flow.md`）。
